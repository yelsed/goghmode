The three tasks

  1. Apply what the hub queued

    Sheets, pins and promotes go through the host's own functions, in the order sent, so a sheet arrives exactly as with direct pairing.

    • A sheet is written as latest.*, also into a drawings folder that does not exist yet.
    • A pin in the same fetch as its sheet points latest.* at that page.
    • An invalid sheet or unknown kind is confirmed and logged, so it cannot block the queue.
    • A write failure stops there: nothing from that item on is confirmed, so it comes again in order.

  2. Fetch and confirm over curl, in a loop

    Two requests per round: get the inbox, confirm what was written. The loop never exits.

    • What was applied is confirmed with its id and version.
    • A failed fetch confirms nothing and reports the error.
    • A 403 from the hub becomes one log line carrying the hub's own reason.

  3. The command, the services, the README

    goghmode receive --hub https://paperclip.procrast.nl:8441, with the interval (5 s) and timeout (20 s) as flags. A systemd unit and a launchd agent ship in contrib/receiver/.

    • receive without --hub is refused.
    • On paperclip: refused until allowed on the hub page, then a queued sheet lands and the hub reports it delivered.

Decisions

ADR-0009 · The receiver calls curl for HTTPS

GoghMode keeps TLS and HTTP frameworks out of its binary (ADR-0004). curl is on macOS and every Arch install, and checks the hub's certificate against the system trust store.

ADR-0010 · A sheet from the hub is written exactly as a host writes it

One code path for what ends up on disk, whatever route a sheet took. Pins behave as with a paired host. A bad item is confirmed and logged; a write error is retried in order.
